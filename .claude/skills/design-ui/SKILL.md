name: design-ui
description: Designs a missing HUD / staff-map layout element (marker, prompt, card, panel, toast, icon) as a self-contained HTML proposal in docs/design/proposals/ that follows the project's design tokens, with 2–3 variants and all states, for the human to judge before any Godot code is written. Usage: /design-ui "warning marker + confirm prompt for a route with incidents" [--area=operational|battle]
---

You are designing a layout element for Eastern Flank: `$ARGUMENTS` (the first quoted part = what is needed; `--area=operational` for the staff map, `--area=battle` for the battle HUD; if missing, infer it from the text, and ask only when it is truly ambiguous). You are a stand-in for Claude Design: the output is a **proposal the human accepts or rejects** – never code in `src/` and never a change to the accepted mockups.

1. **Understand the need.** Read the task / GDD sections the human names (`tools/doc.py gdd "<heading>"`, never whole files). List: what the element says, when it appears, which states it has (normal, hover, selected, disabled, warning, alert…), which data it shows, and what it must not hide. If a task file exists (docs/tasks/), take the wording of its acceptance criteria and playtest steps. Ask the human only about decisions that change the design (e.g. blocking confirmation vs. passive toast).
2. **Load the design language – only what the area needs.**
   - Operational: `docs/design/operational_map/README.md` (verdict + key values: palette, line hierarchy, typography, counters, panels). Open the two HTML files only by grep for the component you are extending (`grep -n` for its class / section), never whole.
   - Battle: `docs/design/README.md` and `docs/design/hud_v3/README.md` (HUD v3 shapes, tokens; `hud-elementy.html` by grep).
   - Both: the code that already exists – Grep `docs/CODEMAP.md` for `UiPalette`, `HudShapes`, `StaffMapPalette` and the nearest existing component (e.g. `StaffMapCountryCard`, `StaffMapContactNotice`, `StaffMapEscalationChip`) and Read its constants (sizes, colours, chamfers). **Reuse its look**; invent a new shape only when none fits and say why.
3. **Design 2–3 variants** (A = closest to existing components, B = alternative placement or weight, C = optional minimal). For each: placement relative to the map/cursor/other panels, size in px at 1440×900, colours as the named tokens (not new hex values – if you need a new token, mark it `NEW TOKEN` with the reason), fonts (Chakra Petch titles/labels, JetBrains Mono numbers, IBM Plex Sans Condensed place names), keyboard hints, and behaviour (what dims, what blocks input, timeout). Respect: fixed-pixel screen-space elements stay readable at every zoom; nothing covers the selected counter or the route; both sides (own blue / enemy red) and colour-blind safety (shape or text carries the meaning, not only colour).
4. **Write the proposal** to `docs/design/proposals/<slug>.html` – one self-contained file (inline CSS, no CDN, fonts via `@font-face` from `../../../assets/fonts/...`), English UI text, in sections: the need, then per variant a 1440×900 or cropped frame showing the element **in context** (a simplified map/HUD backdrop in the project palette) in every state, a spec table (size, colours by token, font, spacing, timing), and a "Godot notes" line (which existing component to extend, which `HudShapes` / `StaffMapPalette` entries). Put a banner at the top: `PROPOSAL – not accepted`, date, and the task id if any. Keep it small (≲ 40 KB).
5. **Check it.** Render it with the headless Chromium from Playwright: `~/.cache/ms-playwright/chromium_headless_shell-*/chrome-headless-shell-linux64/chrome-headless-shell --no-sandbox --screenshot=<out.png> --window-size=1440,900 file://<abs path>` (put the PNG in the scratchpad, ignore the dbus errors), Read the PNG and fix overlaps and clipped text. If that binary is missing, say plainly that you did not see the render.
6. **Hand over.** Tell the human: the file path to open in a browser, one line per variant with your recommendation and why, new tokens (if any), and the open questions. Do not commit. When the human picks a variant: (a) copy the chosen spec into the area's README ("Key values" or a new bullet) and move the file to the area's folder (`docs/design/operational_map/` or `docs/design/hud_v3/`), dropping the PROPOSAL banner; (b) note the decision in the relevant task file so `/implement-task` follows it; only then is a presentation task allowed to implement it (CLAUDE.md: visual work follows the mockups).

Rules: never overwrite or edit an accepted mockup file; never publish the proposal anywhere outside the repo unless the human asks; if the request is really a rules/UX-flow question (not layout), say so and suggest the `game-designer` agent instead.
