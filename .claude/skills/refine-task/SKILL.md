---
name: refine-task
description: Takes a task in status `idea`, interviews the human with multiple-choice questions (each with an open-answer option) and turns it into a fully specified `ready` task (or `blocked` if a dependency is unfinished). Usage: /refine-task TASK-107
model: sonnet
---

You are refining task `$ARGUMENTS` from `idea` to `ready`. If empty, list the `idea` rows with `grep -n "idea" docs/tasks/BACKLOG.md | cut -c1-200` (never read BACKLOG.md whole – ~50 KB) and ask the human which one, using AskUserQuestion. Don't touch tasks in any other status. You orchestrate: you run the interview and the backlog bookkeeping, the `game-designer` agent writes the spec. No code.

1. **Gather context (cheaply)**: read the task's row in BACKLOG.md (`grep -n "TASK-NNN" docs/tasks/BACKLOG.md`), its task file if it has one (a row without a link has none yet), `docs/tasks/_TEMPLATE.md`, and only the relevant GDD / ARCHITECTURE sections (`tools/doc.py gdd` lists headings, `tools/doc.py gdd "<heading>"` prints one; same for `architecture`). Grep `docs/CODEMAP.md` for the code the task would touch. Read the hard dependencies' task files only as far as needed. Never read GDD / ARCHITECTURE / BACKLOG whole.
2. **Find the gaps**: compare the idea with the template. Missing or ambiguous: goal (what the player gains), layers, concrete testable criteria with numbers, edge cases and rejection reasons, playtest steps, player-manual impact, out of scope, dependencies, model (`sonnet` / `opus`). Check the idea against the hard rules in CLAUDE.md (pure core, commands only, data in `.tres`, determinism) and docs/design mockups for visual work. Anything the GDD already decides is **not** asked – use it and cite it.
3. **Interview with AskUserQuestion** (use the tool; don't ask in plain text):
   - 1–4 questions per call, 2–4 options each; put your recommended option first, labelled "(Recommended)", with a one-line trade-off in `description`. Use `multiSelect: true` when the options aren't exclusive. Use `preview` for layouts or code/data shapes the human must compare.
   - The tool adds an "Other" free-text choice automatically – so never add an "Other" option yourself, and phrase options so that a custom answer is a natural fallback. Every question must also stand on its own (the human may not see your earlier text).
   - Ask only what changes the spec: scope boundaries, rule numbers, edge-case behaviour, UI placement, what is out of scope. Pick sensible defaults for the rest and list them as `**[ASSUMPTION]**` in the task (project convention).
   - Work in rounds: after each answer set, decide whether anything is still open; stop at ≤ 3 rounds (~8 questions in total). If an answer opens a bigger design question (new mechanic, balance), ask a follow-up round about it rather than guessing.
   - Treat free-text answers as the human's decisions; if one contradicts the GDD, point it out and ask whether the GDD should change.
4. **Write the spec – delegate to the `game-designer` agent** (it has no AskUserQuestion, so the interview stays in this session; it has no Bash, so you run the backlog script). Pass it: the task ID and current row, the full list of interview questions with the human's answers (verbatim for free-text ones), the assumptions you made, the GDD / ARCHITECTURE headings and code locations you found, and the instructions: create or update `docs/tasks/TASK-NNN-<slug>.md` from `_TEMPLATE.md` (keep the ID; kebab-case slug), one testable line per acceptance criterion with numbers, `Sections` listing the headings to read, `Model` `opus` only for tricky algorithms, determinism, timing or large refactors, the interview decisions (with date) in a short "Decisions" list, everything in English; and update docs/GDD.md where the decisions add or change a rule (it reports which sections it changed). It must not change BACKLOG.md. Afterwards read the resulting task file yourself and check it against the answers; fix gaps with a short follow-up (SendMessage) rather than a new agent.
5. **Split if too big**: a task that clearly exceeds one session (~6 files / ~300 lines per layer) should be split into `a` / `b` tasks (like `TASK-092a`/`b`) – propose the split via AskUserQuestion before doing it.
6. **Backlog**: in BACKLOG.md link the row to the task file, update the title if the scope changed, fix the `Depends on` column (hard deps first, then `(soft: …)`), and set Status to `ready` (plain text; the script adds the icon). Then run `tools/backlog.py --fix` – it turns the status into `blocked` automatically if a hard dependency isn't `done`; tell the human if that happened and which dependency. Run `tools/backlog.py` to confirm it is consistent.
7. **Finish**: show the human a short summary: the task path, the final status, the key decisions, the assumptions to double-check, and the suggested next step (`/implement-task TASK-NNN`). Don't implement and don't commit unless asked (if committing: only the task file and BACKLOG.md, on master – see the project memory).
