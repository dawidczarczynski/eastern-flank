---
name: model-unit
description: Builds or reworks the 3D model of one unit from its unit catalog entry (docs/design/units/units/<id>/) with the unit-modeler agent, then verifies and records the result. Usage: /model-unit leopard_2a4 [--faction=poland]
---

You are building the model for unit `$ARGUMENTS` (first word = unit id, optional `--faction=<id>` for the render; if empty – take the first catalog unit with status `ready_for_model`, sorted by id).

**`--queue` (TASK-183)**: models the `ready_for_model` units that have a `reference.glb`, one after another, sorted by id. Start with `tools/analyze_glb.sh --all` (skips unchanged GLBs, prints the warnings per unit; a unit that failed there is skipped and reported). Then take the first such unit and run all steps below for it as one unit per `unit-modeler` agent run (never several units in one agent). After wrap-up of a unit, re-list the queue (`status` of the others may have changed) and take the next one; stop when none is left or after 3 units per session (context), and list what remains. Each unit's summary also gives the wall time and, from `tools/task_cost.py` where available, the cost, so batch runs can be compared with procedural-only ones.

1. **Check the catalog entry** `docs/design/units/units/<id>/unit.json`: status is `ready_for_model` or `modeled` (a rework), and it has `real_name`, `class`, dimensions (`hull_length`, `width`, `height`), ≥ 3 `silhouette_features` and at least one `side` or `drawing` image. **With a `reference_glb`** the GLB replaces the image and ≥ 1 silhouette feature is enough (shape comes from the GLB). A foot unit (`mobility: foot`, a squad) describes one soldier: it needs only the `height` and any `side` / `front` / `three_quarter` photo, and the render's `Real` line compares only the soldier height. It also needs a non-empty `mechanisms` with `verified` provenance (`provenance["mechanisms.<id>"].verified`); if not, stop and ask the human to declare and verify them in the catalog tool. If something is missing, stop and tell the human what to add in `tools/unit_catalog.sh` – don't model from guesses.
1b. **GLB analysis (step 0 for a unit with `reference_glb`)**: if `reference.glb` exists but `reference_views/glb_sheet.png`, `normalisation.json` or `measurements.json` is missing or older than the GLB, run `tools/analyze_glb.sh <id>` (~1 min; a size mismatch with the catalog stops it – tell the human, don't `--force`). Read its warnings (`normalisation.json`, `measurements.json` → `warnings`) and the sheet. If the GLB file is missing on this computer but `measurements.json` exists, continue with the committed data and say that the IoU gate is unavailable. Run `tools/compare_silhouette.sh <id>` once on an existing model (a rework) to get the starting IoU.
2. **Context for the agent**: the unit's class (`classes.json` → mobility; the declared `mechanisms` with their params and the matching registry entries from `docs/design/units/mechanisms.json` – pivots, help – so the agent copies them into `MECHANISMS`), the faction(s) in `operators`, the human's `feedback` field (for a rework: this is the main input), an existing `blueprint.md` and model file if any, and the closest existing model of the same class in `src/presentation/models/` and its shared parts (reuse, don't copy). For a first model of a class, point to the matching v2 design function (`makeTank` 207–266, `soldier`/`makeInf` 267–299, `makeMLRS` 300–350 in `docs/design/v2/game_screen.scene.js`) and the TASK-031/032/033 file.
3. **Delegate** to the `unit-modeler` agent (its default model) with: the unit id, the catalog path, the faction to render, the points above, and the budgets from the contract test. One unit per run. **For a unit with a GLB also pass**: `docs/design/units/units/<id>/measurements.json` (constants and warnings – take model constants from it, judge low-confidence ones by eye), `reference_views/glb_sheet.png`, the IoU target (`tools/compare_silhouette.sh <id>`, default `--min-iou=0.90` in side, front and top) and the iteration limit: the agent stops at IoU >= threshold or after **4 iterations** (each: build → `render_unit.sh` → `compare_silhouette.sh` → fix the largest `Mismatch:` regions) and reports the final numbers.
4. **Verify yourself**: `tools/check.sh` passes (read the output of `test_unit_mechanisms`: metadata equals the catalog, pivots present); Read the final render sheet the agent reports (`.screenshots/units/<id>_<faction>_sheet.png`) and the battle screenshot; check the stats line (dimensions vs. catalog, triangles, mesh instances). With a GLB run `tools/compare_silhouette.sh <id>` yourself and check the `IoU side=… front=… top=…` line and the `.screenshots/units/<id>_diff_*.png` images; below the threshold after the agent's 4 iterations is not a reason to loop again – report the numbers and the remaining `Mismatch:` lines to the human. If the silhouette clearly doesn't match the references or the model is broken (holes, inverted faces, floating parts), send it back to the agent once with concrete points (SendMessage to the same agent).
5. **Review**: delegate to `reviewer` (default model) for code quality and the contract (no rules in the view, shared meshes, no `randf()`).
6. **Wrap-up**: the catalog entry `status` = `modeled` (keep `feedback` – the human clears it), `blueprint.md` exists. If the unit's `.tres` exists and it's in a roster, mention that it now shows in game. Summarise for the human: render sheet path, the final IoU per view (GLB units) with the iteration count, remaining differences, playtest steps (zoom in, move, attack, hover; the catalog's Model review screen shows render vs. photo). Don't commit unless asked.
