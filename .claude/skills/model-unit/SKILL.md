---
name: model-unit
description: Builds or reworks the 3D model of one unit from its unit catalog entry (docs/design/units/units/<id>/) with the unit-modeler agent, then verifies and records the result. Usage: /model-unit leopard_2a4 [--faction=poland]
---

You are building the model for unit `$ARGUMENTS` (first word = unit id, optional `--faction=<id>` for the render; if empty – take the first catalog unit with status `ready_for_model`, sorted by id).

1. **Check the catalog entry** `docs/design/units/units/<id>/unit.json`: status is `ready_for_model` or `modeled` (a rework), and it has `real_name`, `class`, dimensions (`hull_length`, `width`, `height`), ≥ 3 `silhouette_features` and at least one `side` or `drawing` image. A foot unit (`mobility: foot`, a squad) describes one soldier: it needs only the `height` and any `side` / `front` / `three_quarter` photo, and the render's `Real` line compares only the soldier height. It also needs a non-empty `mechanisms` with `verified` provenance (`provenance["mechanisms.<id>"].verified`); if not, stop and ask the human to declare and verify them in the catalog tool. If something is missing, stop and tell the human what to add in `tools/unit_catalog.sh` – don't model from guesses.
2. **Context for the agent**: the unit's class (`classes.json` → mobility; the declared `mechanisms` with their params and the matching registry entries from `docs/design/units/mechanisms.json` – pivots, help – so the agent copies them into `MECHANISMS`), the faction(s) in `operators`, the human's `feedback` field (for a rework: this is the main input), an existing `blueprint.md` and model file if any, and the closest existing model of the same class in `src/presentation/models/` and its shared parts (reuse, don't copy). For a first model of a class, point to the matching v2 design function (`makeTank` 207–266, `soldier`/`makeInf` 267–299, `makeMLRS` 300–350 in `docs/design/v2/game_screen.scene.js`) and the TASK-031/032/033 file.
3. **Delegate** to the `unit-modeler` agent (its default model) with: the unit id, the catalog path, the faction to render, the points above, and the budgets from the contract test. One unit per run.
4. **Verify yourself**: `tools/check.sh` passes (read the output of `test_unit_mechanisms`: metadata equals the catalog, pivots present); Read the final render sheet the agent reports (`.screenshots/units/<id>_<faction>_sheet.png`) and the battle screenshot; check the stats line (dimensions vs. catalog, triangles, mesh instances). If the silhouette clearly doesn't match the references or the model is broken (holes, inverted faces, floating parts), send it back to the agent once with concrete points (SendMessage to the same agent).
5. **Review**: delegate to `reviewer` (default model) for code quality and the contract (no rules in the view, shared meshes, no `randf()`).
6. **Wrap-up**: the catalog entry `status` = `modeled` (keep `feedback` – the human clears it), `blueprint.md` exists. If the unit's `.tres` exists and it's in a roster, mention that it now shows in game. Summarise for the human: render sheet path, remaining differences, playtest steps (zoom in, move, attack, hover; the catalog's Model review screen shows render vs. photo). Don't commit unless asked.
