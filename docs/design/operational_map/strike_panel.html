Strike panel rework

The need

Since TASK-141a the strike mode holds 12 named weapons (5 Russian, 7 NATO). The TASK-097b panel is a 330 px column of plain toggle buttons with text like "Jassm_er ×6 185 hx" – no glyph, no class, no real range, nothing to tell a Homar-K from an ATACMS, and the other side's weapons are listed too. It has to say, per weapon of the viewer's side only: glyph, name, designation, class, range in km, stock, largest salvo; stock 0 stays listed but greyed (Storm Shadow / Tomahawk until allies deliver); and the player wants a 3D model preview slot for the selected weapon (the models are built in separate tasks; until a model exists the slot shows the class glyph large).

  • When: strike mode (bar button / key S). Docked window, left dock x 16 / y 110, one at a time, X and Esc close, a map click on a target does NOT close it (strike mode keeps the window; the existing rule is unchanged).
  • States: normal, hover, selected (picked weapon), stock 0 (greyed, not hidden, still hoverable for info, not pickable), out of range for the hovered target (hint line, row unchanged).
  • Must not hide: the turn bar rows, the selected counter, the target hex and the range ring – the window only grows downwards from y 110.
  • Colour-blind: side is carried by the tab text ("STRIKE · NATO") and the glyph shape; selection by the amber bar and the bright glyph; stock 0 by opacity and the "0" / "ALLIES" label.
  • Models: a SubViewport with one procedural mesh, slow turntable (12 s per turn, 18° tilt), rendered only while the window is visible and a weapon is picked or hovered (UPDATE_WHEN_VISIBLE, 60 FPS budget safe: one low-poly mesh, no shadows). No model yet → the glyph at 96 px.

Existing frame (reused in all variants): StaffMapWindow – PANEL_STRONG, 1 px LINE, chamfers 0,16,0,16, tab Chakra Petch 700 11 on the side colour, X 32 px. No new tokens in any variant. Data below is real (data/strike/*.tres, NATO side, sorted stock > 0 first, then range descending).

Variant A – docked window with the detail card inside (closest to existing; recommended)

Window widened to 420 px (the width of the report card; the docked-window rule allows 420 for reports – this is the same kind of content). The list is compact 46 px rows; the picked weapon's detail card (model viewport 388×140 + four spec chips) sits under the list; the salvo stepper and the Fire hint close the window. Hover on another row previews its model / chips in the same card (hover pauses back to the picked weapon on leave). One component, no floating layers.

Variant B – narrow list + floating flyout card

The panel stays 330 px (unchanged width, rows with a bigger 56 px thumbnail and the stock on the right). The detail card is a separate 320 px chamfered plate that opens to the right of the window (x 362) for the hovered / picked weapon and carries the large model (320×190) and the spec table. More room for the model; two layers and the card covers more of the map while hovering.

Variant C – list only, models shown where they matter

Minimal: the panel stays 330 px, rows get glyph + name + designation + class + km + stock and no preview at all. The 3D model is shown only on the confirm card (the "3 × JASSM-ER on Chernyakhovsk" card) as a 120×70 side view, and on the result report header. Cheapest, no extra viewport while the player browses, but the player has to pick a weapon to ever see it.

Recommendation

A. It is one docked window with the existing frame, keeps the model in view while the player compares weapons by hovering, puts nothing over the map beyond the window itself and costs one SubViewport. B gives a bigger model but doubles the layers; C is the fallback if the live viewport proves too heavy. Open questions: (1) 420 px width for a docked window other than reports – OK? (2) Russian side: the same layout with side.enemy tab, 5 rows and no greyed ones – OK? (3) Should the stock-0 weapons be sorted last (as drawn) or stay in range order?
