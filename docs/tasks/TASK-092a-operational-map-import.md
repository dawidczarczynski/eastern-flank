# TASK-092a: Operational map from real data – importer profile, tiled download, the Suwałki theatre map (5 km hexes, ~340 × 277 km)

- **Status**: done
- **Layers**: tools (Python, offline) + data + docs (ADR amendment, credits)
- **Depends on**: TASK-087, TASK-108
- **Model**: opus (geodata over a ~94 000 km² area, tiled download, coastline, determinism, import size and time)
- **Topic**: Two-layer game

## Goal

The operation is played on a real **regional theatre** around the Suwałki Gap – north-east Poland, the Kaliningrad oblast, southern Lithuania and western Belarus (human decision 2026-11-01, GDD "Operational layer" → "Theatre", "Operational map"): a 5 km hex map imported from the same real data as the battle maps, big enough that attacking Kaliningrad or Belarus is a real option on the map. Reworked 2026-11-01 from the earlier 20 × 16 Suwałki Gap map.

## Acceptance criteria (testable)

Importer (`tools/import_map.py`, Python tests in `tools/test_import_map.py`):

- [x] New option `--profile=tactical|operational` (default `tactical`; tactical output byte-identical to today – the existing golden test stays green unchanged).
- [x] `operational` sets: hex default 5000 m, sample lattice **250 m** (`--sample=` overrides; tactical keeps 25 m), DEM **Copernicus GLO-90** (`--dem=glo30|glo90`, default `glo90` for `operational`, `glo30` for `tactical`; GLO-90 COG tiles `Copernicus_DSM_COG_30_N<lat>_00_E<lon>_00_DEM.tif` from the same open bucket, cached under `~/.cache/eastern-flank/maps/dem/`; the reader handles both tile widths – test on a synthetic GLO-90-sized fixture tile), and the classification in GDD "Operational map": water share ≥ 0.50 → water; urban ≥ 0.15 → urban; forest ≥ 0.50 → forest; marsh ≥ 0.25 → marsh; relief ≥ 60 m → hills (default tuned to 35 m, see Implementation notes); else plains (never fields). Thresholds are CLI options with these defaults (`--water-share`, `--urban-share`, `--forest-share`, `--marsh-share`, `--hills-relief`).
- [x] Unit tests of the operational classifier with synthetic counts: 50 % water / 50 % forest → water; 49 % water, 51 % forest → forest; 15 % urban + 60 % forest → urban; 49 % forest, 26 % marsh → marsh; 49 % forest, 0 % marsh, relief 60 m → hills; same with relief 59.9 m → plains; 100 % farmland → plains.
- [x] Roads in `operational`: only `highway` motorway / trunk / primary / secondary and their `_link`s (a `tertiary` way gives no link – test); rivers: only `waterway` river / canal (a named `stream` gives no link – test). The corner-clip length scales with the hex: `CLIP_M × hex / 250` (800 m at 5 km; test with a line clipping a corner by 700 m → no link, 900 m → link).
- [x] **Tiled Overpass download**: the `operational` query asks only for what the profile reads (forest / wood, water, wetland, the urban `landuse` values, the four road classes, river / canal) **plus** `natural=coastline` ways and `boundary=administrative` + `admin_level=2` ways (country borders – read by TASK-113, downloaded now so TASK-113 runs offline). The map's bbox (+ 500 m) is split into tiles on a fixed **0.5° × 0.5°** grid aligned to multiples of 0.5° (`--tile-deg=` overrides; tiles reusable by other maps), each cached as its own file under `~/.cache/eastern-flank/maps/osm/`. A failed tile is retried (up to 3 times, with a pause) and the run continues where it stopped (finished tiles are never fetched again). `--offline` with a complete cache never downloads (test with a fake cache); a missing tile fails with a clear message naming the tile.
- [x] **Tiling does not change the result**: tiles are processed one at a time (only one tile's JSON in memory); areas that appear in several tiles are rasterised again with the same "higher class wins" rule, which is idempotent. Test: the synthetic operational fixture imported with one tile and with 4 tiles (`--tile-deg` small enough) gives byte-identical output.
- [x] **Sea from the coastline**: OSM has no sea polygons, so `natural=coastline` ways are rasterised as barriers on the sample lattice and a 4-connected fill from `--sea-seed=<lat,lon>` points (repeatable; the `operational` profile has built-in defaults for the theatre: one in the open Baltic, e.g. 55.30 N 20.60 E, one in the Curonian Lagoon, e.g. 55.10 N 21.05 E – the agent verifies both on a map) marks the reached points as water. Water polygons that already cover the sea (`natural=bay`, `water=lagoon`) are unaffected. Test: a synthetic fixture with a coastline and a seed → the points on the seed's side are water, the land side is not; a seed on land → error.
- [x] Determinism: a synthetic fixture imported with `--profile=operational --hex=1000` (fixtures in `tools/import_map_fixtures/`, regenerated by `--make-fixtures`; including a coastline and a tile boundary) is byte-identical to a committed golden `tests/fixtures/maps/sample_op_map.tres` and to a second run.

**Decisions**

- **Centre moved 0.012° west to 54.20 N 22.888 E** (allowed ≤ 0.1°): at 22.90 E Kaliningrad lands on column 1 (1 hex from the edge). At 22.888 E Kaliningrad (2, 19), Olsztyn (2, 43) and Lida (65, 38) are exactly 2 hexes inside; 22.85 E would push Lida to column 66. Size unchanged (68 × 64).
- **Hills threshold tuned 60 m → 35 m**, and made the profile's default (`OP_HILLS_RELIEF`), so the importer default and the GDD agree; the spec's 60 m / 59.9 m boundary test now passes `hills_relief=60.0` explicitly, a new test checks 35 / 34.9 m at the default, and the operational golden changed by one hex ((5, 1) P → H). Other thresholds unchanged.
- The relief of a hex is the 90th − 10th percentile of its open points (forest, urban and water points dropped when ≥ ¼ of the hex is open, as on tactical maps).

**Measurements**

- OSM: **72 tiles** of 0.5° (52.5–55.5 N, 20.0–26.0 E), **1.85 GB** of JSON (6 KB for an open-sea tile to 69 MB for Vilnius), first download ≈ **1 h 47 min**: 66 tiles on 2026-11-02 (08:52–10:34, ~1 h 42 min, one session), the last 6 on 2026-11-07 in 5 min (40–60 s each, no retries). The public Overpass server answered every tile at 0.5° (query timeout 900 s) – `--tile-deg` did not need reducing. DEM: 24 GLO-90 tiles, 84 MB, ~10 s. Cache for the theatre ≈ 1.9 GB (`~/.cache/eastern-flank/maps/osm/op1_*` + `dem/*_COG_30_*`).
- Offline import: **4 min 22 s** wall (target ≤ 20 min), **0.90 GB** peak memory (max RSS, `/usr/bin/time -v`); the earlier run with the download took 9 min 59 s (307 s inputs + 291 s import). Two imports of the same cache are byte-identical (the online run and an offline run differed only in the `display_name` given).
- `.tres`: **79 KB** (78 786 bytes). Load 8 ms; `to_grid()` 57–60 ms (median of 3; the test's limit is 1 s); +1.5 MB of static memory per built grid (`OS.get_static_memory_usage`), +0.2 MB for the loaded resource.
- `HexGrid.path_to`, unlimited budget: tile (0, 0) is open Baltic (WATER), so a path from it is empty immediately (0 ms); the baseline is from the first land tile connected to the south-east corner, **(0, 13) → (67, 63): 0.24 s, 95 steps** (median of 3). `reachable` from (67, 63) over the whole map: 0.24 s, 4 169 tiles. TASK-092c's planner must beat this (budget 30 ms).

**Known limitations**

- **Country borders incomplete**: most Polish–Russian and Lithuanian–Russian border ways carry no `boundary` / `admin_level` tags of their own (they are only members of the country relations), so the `way["boundary"="administrative"]["admin_level"="2"]` clause the spec asked for misses them. TASK-113 needs an extra, small borders-only query per tile (e.g. `relation["boundary"="administrative"]["admin_level"="2"](bbox); way(r)(bbox);` under a new query version) – the land-cover tiles need not be downloaded again. Human decision whether that goes into TASK-113.
- **River and road links are dense**: 2 147 river hexes (49 %) and 2 659 road hexes (61 %); `waterway=canal` includes many drainage canals in the Kaliningrad lowland. Fine for the tests; TASK-092b/c may want a minimum length or a named-only rule for rivers.
- Lakes under half a hex (Wigry, Hańcza, Vištytis) and the Curonian Spit vanish at 5 km – the paper-map view (TASK-112) should draw them from finer data.
- The OSM tiles are from two dates (2026-11-02 and 2026-11-07); a re-download gets today's OSM.
- Environment note: `gdformat` / `gdlint` in `~/.local/bin` were installed for Python 3.8 and fail under the system's Python 3.12 (`No module named 'gdtoolkit'`) – also the format hook. For `tools/check.sh` the agent used a gdtoolkit 4.5.0 copy installed into its scratchpad (`pip install --target`); the human should reinstall gdtoolkit (`pipx install 'gdtoolkit==4.*'`).
